# 0002. パスキーのみによる認証

## 状態

採用

## 背景

アプリケーションに認証基盤が無かった。AGENTS.md では次の方針が既に定められていた。

- ASP.NET Core Identity の Cookie 認証を使う。
- 認証情報を localStorage に保存しない。
- 更新 API では CSRF トークンを必須にする。

パスワードを扱わずにフィッシングに強い認証にするため、パスキー(WebAuthn)のみで認証したい。パスキーだけにすると、次の 3 点を決める必要がある。

- 初回登録での本人確認
- パスキーをすべて失ったときの復旧
- 開発・テスト環境での扱い

## 検討した選択肢

- パスキーの実装
  - 案A: .NET 10 の ASP.NET Core Identity に組み込まれたパスキー機能(`SignInManager.MakePasskeyCreationOptionsAsync` など)。追加の依存が無く、Identity のユーザー・セキュリティスタンプ・Cookie とそのまま連携できる。SPA 向けの `MapIdentityApi` はパスキーに対応していないため、API は自前で作る。
  - 案B: Fido2NetLib などの外部ライブラリ。attestation 検証などの機能は多いが、Identity との連携と資格情報の保存を自前で書く必要がある。
- 初回登録の本人確認
  - 案A: 自己登録＋メール確認。誰でも登録できるが、メールアドレスの所有を確認してからパスキーを登録する。
  - 案B: 招待制。最初の管理者を作る別の手段が必要になる。
  - 案C: 確認なし。他人のメールアドレスで登録できてしまう。
- パスキーをすべて失ったときの復旧
  - 案A: メールで復旧リンクを送る。メールアカウントを乗っ取られると、アカウントも乗っ取られる。
  - 案B: リカバリーコード。利用者が保管していなければ使えない。
  - 案C: 管理者による再設定のみ。運用の負荷はあるが、実装は小さく、本人確認を人が行える。
  - 案D: 復旧手段なし。ロックアウトしたら救済できない。

## 決定

- Identity 組み込みのパスキー機能を使う(案A)。スキーマは `IdentitySchemaVersions.Version3`。
- 認証はパスキーのみとし、パスワードは持たない。
  - `UserVerificationRequirement = "required"`：生体認証または PIN を必須にする。
  - `ResidentKeyRequirement = "required"`：ユーザー名を入力せずにサインインできるようにする。
- 登録は自己登録＋メール確認とする(案A)。
  - メールのリンクに含める「パスキー設定トークン」(有効期限 24 時間)で、パスキーの登録を許可する。
  - パスキーの登録に成功した時点で、メールアドレスを確認済みにする。
- 復旧は管理者による再設定のみとする(案C)。
  - システム管理者が、対象ユーザーの全パスキーを削除してセキュリティスタンプを更新し、同じパスキー設定トークンのリンクをメールで送る。
- パスキー設定トークンは使い捨てにする。登録に成功したらセキュリティスタンプを更新して無効化する。
- 最後の 1 つのパスキーは削除できないようにする。
- 最初の管理者は `grant-system-admin` コマンドで付与する。

## 理由

- Identity 組み込みのパスキーを使えば、既存の Cookie 認証・ロール・セキュリティスタンプによるセッション失効がそのまま使え、依存も増えない。
- 本人確認のメールリンクと復旧のリンクを同じトークンの仕組みにすると、検証すべき経路が一つで済む。
- メールによる自動復旧は、メールアカウントを乗っ取られるとアカウントも乗っ取られる。そのため、本人確認を人が行う管理者の再設定に限定した。最後のパスキーを削除できなくして、自分でロックアウトする経路を減らす。
- 管理者権限を設定値で自動付与すると、設定ミスがそのまま権限昇格になる。そのため、明示的なコマンドに限った。

## 影響

- 利用者がパスキーをすべて失うと、管理者が対応するまで利用できない。管理者は本人確認の運用手順を用意する必要がある。
- メール送信の基盤が必要になる。開発では Mailpit で受け取る。本番では SMTP の設定(`Smtp:*`)が必要。
- WebAuthn は HTTPS または `localhost` でしか動かない。開発での動作確認は `http://localhost:5000`(バックエンドが配信する SPA)で行う。Vite の開発サーバー(`:5173`)は Origin が異なるため、認証は使えない。
- 管理者の再設定から既存セッションが失効するまでに、最大でセキュリティスタンプの検証間隔(1 分)の遅れがある。
- 統合テストでは実際の認証器を使えない。WebAuthn の応答を組み立てるテスト用のソフトウェア認証器で検証する。
- メールアカウント以外の復旧手段(リカバリーコードなど)が必要になった場合は、この決定を見直す。
