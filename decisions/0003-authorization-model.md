# 0003. 認可の基本方針とテナント所属モデル

## 状態

採用

## 背景

認証(0002)を先に実装する。リポジトリはマルチテナント構成を想定しており、ユーザーとテナントの関係は、ユーザーテーブルの形や登録の流れに影響する。そのため、認可の実装に先立って骨格だけを決めておく。ロールや権限の細目は後で決める。

## 検討した選択肢

- ユーザーとテナントの関係
  - 案A: ユーザーはシステム全体で 1 つとし、複数のテナントに所属できる。所属とテナント内ロールは中間テーブルで持つ(Slack や GitHub Organization と同じ形)。
  - 案B: ユーザーは 1 つのテナントに専属する。同じ人が別のテナントを使うには別アカウントが必要。
- テナント内ロールの保持先
  - 案A: Identity のロール(AspNetUserRoles)。テナントの区別ができない。
  - 案B: 所属テーブル(TenantMembership)の列。テナントごとにロールを持てる。
- 既定の認可
  - 案A: 既定は許可し、保護する API に個別で `[Authorize]` を付ける。付け忘れると公開されてしまう。
  - 案B: 既定は拒否(FallbackPolicy で認証必須)とし、匿名で使う API だけを `[AllowAnonymous]` にする。

## 決定

- ユーザーとテナントは案A とする。1 ユーザーが複数のテナントに所属する。
- 認可は 2 層に分ける。
  - システム全体のロール：Identity のロールで持つ。現時点では `SystemAdmin` のみ。
  - テナント内のロール：将来の `TenantMembership`(UserId・TenantId・Role)で持つ。
- テナントの文脈は `/api/tenants/{tenantId}/…` のルートで受け取る。所属とロールは、DB を参照するポリシーハンドラーで判定する。テナント内ロールは Cookie の Claim に載せない。
- 既定の認可は案B(既定拒否)とする。SPA のシェル(`index.html`)と、存在しない `/api` への 404 は匿名で許可する。
- 今回実装するのは、既定拒否と `SystemAdmin` ロールだけ。テナント・所属・テナント内ロールは、テナント機能の実装時に追加する。

## 理由

- 1 人が複数の組織に参加する使い方を想定する場合、ユーザーをテナントごとに分けると、アカウントとパスキーの重複管理が利用者の負担になる。
- テナント内ロールを Claim に載せると、所属やロールを変えても Cookie の期限まで古い権限が残る。DB を参照して判定すれば、変更が即座に反映される。
- 既定拒否にしておけば、API を追加したときに `[Authorize]` を付け忘れても公開されない。

## 影響

- 新しい API は既定で認証必須になる。匿名で公開する API には `[AllowAnonymous]` を明示する。
- テナント機能の実装時に、`TenantMembership` エンティティ、所属を確認するポリシー、テナント内ロールの一覧を設計する。必要に応じて、この方針を具体化する ADR を追加する。
- 画面側の表示制御(管理メニューを隠すなど)は利便性のためだけに行う。認可は常に API 側で行う。
